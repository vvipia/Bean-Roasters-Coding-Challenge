# Bean Roasters Coding Challenge

각자의 수준에 맞는 문제를 꾸준히 풀고, 서로의 풀이를 나누며 성장하는 팀 코딩테스트 스터디입니다.
문제를 많이 푸는 것만큼 **직접 고민하고, 이해한 내용을 설명하는 것**을 중요하게 생각합니다.

스터디는 **파이널 프로젝트 이전인 11월 11일까지** 진행합니다.

## 기본 규칙

- 매주 **공통 문제 1개**를 정해 함께 풉니다.
- 각자 **주마다 최소 3개 문제**를 풉니다.
- 주 1회 모임에서 공통 문제와 각자 푼 문제 중 1개를 리뷰합니다.
- 개인 문제는 팀원별 학습 범위에 맞춰 선택합니다.
- 여유가 있다면 최소 목표에 그치지 않고 추가로 도전합니다.

### 1. 주간 진행 방식

- 한 주는 월요일부터 일요일까지이며, 일요일까지 풀이를 PR로 제출합니다.
- 주간 최소 3개에는 공통 문제를 포함합니다. **공통 1개 + 개인 2개 이상**이 기본입니다.
- 다음 주 공통 문제는 팀원들이 번갈아 제안하고, 함께 도전할 수 있는 문제로 정합니다.
- 목표를 채우기 어렵다면 미리 공유하고 가능한 분량과 보완 계획을 남깁니다.

### 2. 풀이 제출 방식

- 제출 경로: `src/<본인 폴더>/<주차>/<문제 이름>/`
- 예시: `src/vvipia/week01/pokemon/`
- 문제별 디렉터리에 풀이 코드와 `README.md`를 함께 제출합니다.

| 파일 | 작성 내용 |
| --- | --- |
| 풀이 코드 | 직접 작성한 문제 풀이 |
| `README.md` | 문제 이름과 링크, 접근 방법과 핵심 아이디어, 막혔던 부분이나 새로 배운 점, 참고 자료 출처 |

- 커밋 메시지는 작업 내용을 알 수 있게 작성합니다.
  - 풀이 추가: `solve: 폰켓몬 풀이 추가`
  - 오류 수정: `fix: 폰켓몬 중복 처리 수정`
  - 설명 추가: `docs: 폰켓몬 풀이 설명 추가`
- 다른 팀원의 파일을 수정해야 한다면 먼저 이야기합니다.
- 한 주가 끝나면 `src/<본인 폴더>/<주차>/retrospective.md`에 주간 회고를 작성합니다. 양식은 5번을 참고하세요.

### 3. 브랜치·PR·병합 규칙

**개인 브랜치를 계속 유지하고, PR 승인 후 일반 머지로 제출 내용을 반영합니다.**

| 브랜치 | 용도 |
| --- | --- |
| `main` | 팀원이 확인한 풀이와 학습 기록을 모으는 브랜치 |
| `ster1046-ux` | 해당 팀원의 개인 작업 브랜치 |
| `kkqor0702` | 해당 팀원의 개인 작업 브랜치 |
| `kongsni` | 해당 팀원의 개인 작업 브랜치 |
| `jinni1` | 해당 팀원의 개인 작업 브랜치 |
| `vvipia` | 해당 팀원의 개인 작업 브랜치 |

**작업 순서**
1. 최초에 `main`에서 본인의 개인 브랜치를 만듭니다.
2. 개인 브랜치에서 본인 폴더에 풀이와 설명을 작성합니다.
3. 작업 내용을 커밋하고 개인 브랜치에 push합니다.
4. **개인 브랜치 → `main`** 방향으로 PR을 생성합니다.
5. Slack 팀 채널에 PR 확인 메세지를 남깁니다.
6. 작성자 외 **팀원 1명 이상이 제출 내용을 확인하고 승인**합니다. (승인은 아무나 하셔도 됩니다.)
8. 승인 후 **Create a merge commit**으로 병합합니다.
9. 병합 후에도 개인 브랜치를 삭제하지 않고 다음 제출에 계속 사용합니다.

**PR 작성 예시**
- 제목: `[vvipia] week01 풀이 제출`
- 본문: 제출한 문제·학습 목록, 통과 여부 또는 진행 상태, 질문이나 확인받고 싶은 부분
- 풀이를 나누어 제출하는 경우에도 제목에 해당 주차와 제출 내용을 표시합니다.

**확인·병합 기준**
- 확인자는 제출 경로, 풀이 코드, 설명 파일이 갖춰졌는지 확인합니다.
- 상세 풀이 리뷰는 주간 모임에서 진행하며, PR에서도 질문과 의견을 남길 수 있습니다.
- `main`에는 직접 push하지 않고 PR을 통해 반영합니다.
- **Squash and merge와 Rebase and merge는 사용하지 않습니다.**
- 일반 머지를 사용하면 개별 커밋과 병합 관계가 보존되어 GitKraken 등에서 작업 흐름을 확인할 수 있습니다.
- 브랜치를 새로 만들거나 강제로 초기화하지 않고 기존 개인 브랜치에서 작업을 이어갑니다.
- 공통 설정 등 최신 `main`의 변경이 필요하면 개인 브랜치에 `main`을 merge합니다. 충돌이 발생하면 관련 팀원과 확인하여 해결합니다.

> 저장소 설정: PR 승인 최소 1명, Allow merge commits 활성화, Squash/Rebase 병합 비활성화, Automatically delete head branches 비활성화  
> Ruleset 이름: `submission-review` / 적용 대상: `main` / 상태: `Active`

### 4. 함께 공부하는 방식

- 공통 문제는 먼저 스스로 고민한 뒤 다른 풀이를 확인합니다.
- 막히면 시도한 방법과 이해되지 않는 부분을 함께 적어 질문합니다.
- 해설이나 AI의 도움을 받았다면 내용을 이해하고 직접 다시 작성합니다. 참고한 부분도 기록합니다.
- 정답 여부뿐 아니라 변수 이름, 가독성, 자료구조 선택, 시간 복잡도도 함께 살펴봅니다.
- 리뷰는 사람을 평가하기보다 코드와 접근 방법에 대한 구체적인 의견으로 남깁니다.
- 매주 다른 팀원의 풀이를 하나 이상 읽고, 배운 점이나 질문을 남기는 것을 권장합니다.
