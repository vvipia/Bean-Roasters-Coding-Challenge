### 2. 새로 배운 점

- **문자열 분리와 연속된 공백 처리**
    - **관련 문제:** Solution 1 — OX퀴즈 (`solution1`)
    - 최초 풀이에서는 `split(" ")`으로 수식을 나누고 `Integer.parseInt()`로 숫자를 변환하였다.
    - 풀이 이후 공백이 여러 개일 때 빈 문자열이 생기는 이유와 처리 방법을 질문하였다.
    - `split(" +")`는 연속된 스페이스를, `split("\\s+")`는 스페이스와 탭 등 연속된 공백 문자를 구분자로 처리한다.
    - 앞뒤 공백도 허용하려면 `trim().split("\\s+")`처럼 먼저 제거할 수 있다.
    - 코드 리뷰에서는 연산 결과를 먼저 구하고 정답 판정을 한 번만 하면 덧셈과 뺄셈 분기의 중복을 줄일 수 있음을 확인하였다.

- **수열의 규칙과 합 공식 활용**
    - **Solution 2 — 다음에 올 숫자 (`solution2`):** 처음 세 원소의 차이를 비교하여 등차수열과 등비수열을 구분하고, 마지막 원소에 공차를 더하거나 공비를 곱하였다.
    - **Solution 3 — 연속된 수의 합 (`solution3`):** 원소 개수의 홀짝에 따라 첫 값을 계산한 뒤 연속된 정수를 배열에 채웠다.
    - 풀이 이후 연속된 수의 합을 `total = first × num + num × (num - 1) / 2`로 나타내면 홀짝 분기 없이 첫 값을 구할 수 있음을 학습하였다.
    - 현재 코드는 최초의 홀짝 분기 방식을 유지하고 있으며, 합 공식은 추가로 학습한 접근이다.

- **여유 공간을 둔 2차원 배열의 경계 처리**
    - **관련 문제:** Solution 4 — 안전지대 (`solution4`)
    - 한 변이 N인 원본보다 두 칸 큰 배열을 만들고, 원본 좌표를 한 칸씩 이동시켜 위험 지역을 표시하였다.
    - 지뢰가 모서리에 있어도 주변 9칸을 범위 검사 없이 표시할 수 있도록 구현하였다.
    - 위험 지역이 겹쳐도 마지막에 0이 아닌지만 검사하므로 같은 칸을 중복 차감하지 않는다.
    - 위험 표시에는 여유 공간을 사용하고, 집계할 때는 실제 원본에 대응하는 영역만 확인하였다.
    - 코드 리뷰에서는 위험 여부만 필요하면 boolean 배열을 사용할 수 있고, 고정된 3 × 3 반복문으로 표시 코드를 정리할 수 있음을 확인하였다.

- **조건을 검사하는 순서와 경우의 수 분류**
    - **관련 문제:** Solution 5 — 주사위 게임 3 (`solution5`)
    - 네 숫자 일치, 세 숫자 일치, 두 쌍, 한 쌍, 모두 다름 순서로 조건을 검사하였다.
    - 앞에서 더 많은 숫자가 같은 경우를 제외했기 때문에 뒤쪽 분기에 불필요한 불일치 조건을 추가하지 않아도 된다.
    - 풀이 이후 정렬하면 같은 숫자가 모여 위치별 비교 조건을 줄일 수 있다는 대안을 학습하였다.
    - 실제 풀이는 정렬 없이 모든 위치 조합을 직접 비교하는 방식이다.

- **유클리드 호제법과 기약분수**
    - **관련 문제:** Solution 6 — 분수의 덧셈 (`solution6`)
    - 두 분모의 곱으로 통분한 다음 분자와 분모를 최대공약수로 나누어 기약분수를 만들었다.
    - 최대공약수 계산 방법을 다시 찾아보았고, 문제별 회고에는 이 부분을 AI 질문 O로 기록하였다.
    - `gcd(a, b) = gcd(b, a % b)` 관계를 반복하여 b가 0일 때의 a를 반환하는 방법을 정리하였다.
    - 코드 리뷰에서는 동일한 최대공약수를 두 번 계산하는 대신 변수에 저장하여 재사용할 수 있음을 확인하였다.

- **구간 정렬과 시작 포함·끝 제외 범위**
    - **관련 문제:** Solution 7 — K번째수 (`solution7`)
    - 최초 풀이에서는 원본 전체를 `clone()`으로 복사하고 필요한 구간만 정렬하였다.
    - 구간을 잘라내지 않았으므로 k번째 원소의 위치를 `(i - 1) + (k - 1)`로 계산하였다.
    - 풀이 이후 `Arrays.sort()`와 `Arrays.copyOfRange()`의 범위가 `(a, b]`인지 질문하고, 실제로는 `[a, b)`임을 정리하였다.
    - 시작은 포함하고 끝은 제외하므로 구간 길이는 `b - a`이며, 전체 배열은 `[0, array.length)`로 표현할 수 있다.
    - `Arrays.copyOfRange()`로 구간만 복사하면 새 배열의 시작이 0이 되어 정답 위치가 `k - 1`로 단순해진다.

- **두 원소를 이어 붙여 비교하는 정렬 기준**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - 처음에는 `res()`로 숫자의 자릿수를 보정한 우선순위 값을 계산하려고 하였다.
    - 풀이 중 AI의 힌트를 받아 숫자 자체의 크기가 아니라 두 숫자를 이어 붙인 `ab`와 `ba`를 비교하는 방식으로 변경하였다.
    - 3과 34는 `343 > 334`이므로 34가 먼저이고, 3과 30은 `330 > 303`이므로 3이 먼저이다.
    - `ba.compareTo(ab)`를 반환하면 더 큰 조합이 되는 순서로 배치할 수 있다.
    - Comparator는 두 원소만 비교하지만, 정렬 기능이 이 비교를 반복하여 전체 순서를 만든다는 점을 질문하고 정리하였다.

- **정렬 API와 Comparator의 역할 구분**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - `int[]`에 `Arrays.sort(numbers, comparator)`를 사용할 수 있는지 질문하였다. 기본형 배열에는 Comparator를 직접 전달할 수 없다.
    - `Integer[]`를 사용하거나 Stream에서 `boxed()`로 변환하면 비교 기준을 전달할 수 있다.
    - `Arrays.sort()`는 배열, `Collections.sort()`는 List, `Stream.sorted()`는 Stream을 정렬한다.
    - `Collectors`는 Stream 결과를 모으는 도구이고, `Comparator`는 두 값을 비교하는 기준이라는 차이를 정리하였다.
    - `Comparator.comparing()` 사용 가능 여부도 질문하였다. 각 원소에서 기준값을 추출할 때 적합하며, 이 문제처럼 두 원소를 함께 사용해 비교하려면 두 인자 람다가 적합하다.
    - 중괄호를 사용하는 비교 람다에는 return이 필요하고, 비교 결과는 double이 아니라 int여야 한다.

- **예외 입력과 문자열 누적 비용**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - 최초 코드에서는 모든 원소가 0일 때 `"000"`처럼 반환되는 경우를 놓쳤다.
    - 리뷰 이후 정렬된 첫 원소가 0이면 `"0"`을 반환하는 처리를 추가하였다.
    - `answer += number`는 누적 문자열을 반복해서 복사하므로 최악 O(N²)의 비용이 발생할 수 있다.
    - `StringBuilder.append()`로 누적하면 결합 비용을 줄여 전체 풀이를 O(N log N)으로 개선할 수 있음을 배웠다.
    - 현재 파일에는 문자열 += 방식이 남아 있으므로 StringBuilder는 아직 적용하지 않은 개선 사항이다.

### 3. 막힌 부분 / 함께 이야기하고 싶은 내용

- **숫자 하나의 우선순위로 정렬하려던 접근**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - 자릿수에 따라 나누고 값을 보정하는 res() 함수를 만들었지만 올바른 기준을 정하는 데 막혔다.
    - AI가 두 숫자를 이어 붙여 비교하라고 설명했을 때 처음에는 의미가 바로 이해되지 않았다.
    - 3과 34의 비교에서 단순히 끝자리 4가 3보다 크기 때문인지 질문하였고, 전체 연결 결과에서 처음 달라지는 자리를 비교한다는 점을 정리하였다.

- **두 원소의 비교가 전체 정렬로 이어지는 과정**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - 두 숫자만 비교하는 코드로 배열 전체를 정렬할 수 있는지 의문이 들었다.
    - 비교 함수가 한 번에 두 원소의 순서를 결정하고, sorted()가 그 함수를 반복 호출한다는 역할 분담을 학습하였다.
    - `ba.compareTo(ab)`의 부호에 따라 실제로 어느 원소가 앞에 오는지 작은 예제로 다시 확인하고 싶다.

- **정렬 관련 이름과 배열 타입 혼동**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - Collections, Collectors, Comparator의 이름과 역할이 헷갈려 차이를 질문하였다.
    - 현재 Solution.java의 main()에는 `int[]`에 Comparator를 전달하는 `Arrays.sort(numbers, ...)` 실험 코드가 남아 있다. 이 호출은 컴파일되지 않는다.
    - int[]의 기본 정렬과 Integer[]의 사용자 정의 정렬을 구분하여 복습할 필요가 있다. 이 main()의 오류는 solution() 내부의 연결 비교 로직과 구분해서 점검해야 한다.

- **구간의 끝을 제외하는 규칙**
    - **관련 문제:** Solution 7 — K번째수 (`solution7`)
    - fromIndex와 toIndex가 어느 쪽을 포함하는지 헷갈렸고, 끝을 제외하는 이유도 질문하였다.
    - `[a, b)`를 “a부터 b 직전까지”로 읽고, `for (int i = a; i < b; i++)`와 같은 범위라는 점으로 연결하였다.
    - 1부터 시작하는 문제의 위치와 0부터 시작하는 Java 인덱스를 나누어 계산하는 연습이 필요하다.

- **문자열 분리 결과의 빈 원소**
    - **관련 문제:** Solution 1 — OX퀴즈 (`solution1`)
    - 공백이 여러 개일 때 split 결과에 빈 문자열이 나타나 한 덩어리의 공백으로 처리하는 방법을 질문하였다.
    - 연속 공백 처리와 앞뒤 공백 제거는 구분해야 한다. `split(" +")`만으로 선행 공백까지 제거되는 것은 아니므로 trim()의 역할도 함께 기억하고 싶다.

- **정답 로직과 실행 비용을 함께 점검하기**
    - **관련 문제:** Solution 8 — 가장 큰 수 (`solution8`)
    - 정렬 기준을 구현한 뒤에도 모든 값이 0인 입력을 별도로 처리해야 했다.
    - 문자열 누적 비용까지 고려하면 정렬이 O(N log N)이더라도 전체 풀이가 최악 O(N²)이 될 수 있음을 확인하였다.
    - 정렬 기준, 예외 입력, 결과 문자열 생성 비용을 각각 점검하는 습관을 들이고 싶다.
